# Answers to KIT-SPEC.md

1. Behind a door stands one synchronous function per heir, and one for the zero head. The door hands it `{ method, args (raw JSON text) }`, and the function returns `{ object: raw JSON text, seen, at? }` or `null` for silence (`lib/quo.js`, `reaches`). It is handed no more, because none of these functions reads more.
2. The ward holds its own keys. The things behind the door get no handle back to the ward, and nothing removes one because none is given.
3. Nothing answers the zero head unless the ward is made with a `zero` function, and then that one function answers every zero head ask. The harness sets it from `reach` on `ward`. A ward made without one refuses every zero head ask as case 4, because this kit gives no way to add one later. The zero head keeps no relation. So the same sealed bytes presented twice are answered twice, each time from a fresh reply ephemeral. What may answer there is what may run twice on the same bytes, and every function of this kit qualifies, because each keeps nothing between asks.
4. One. `Ward.arrive` is synchronous from opening the box to moving the keys. Two arrivals at one moment are so judged one after the other, and the key a choice is made under is the key the door held when it made it. This is the cheapest answer that keeps the move's tables true, and it needs no lock.
5. The parts are `Ward`, `Standing`, `arrive`, `invite`, `release`. A relation is keyed by its heir pk in hex.
6. The seed is handed in as 32 bytes, or as text or bytes that get hashed. It is held in memory as derived key objects only. A ward holds one lock, for every invitation it gives, because one is all a door needs to read a knock. It is drawn when the `Ward` is constructed and is held in memory. The ward does not keep a heir's secret after giving the invitation.
7. `node:crypto` `randomBytes`, and Node's ML-KEM for the lock and each encapsulation.
8. In memory, in a `Map`, per heir: fresh, or `H`, `V`, `O`, `F` and the highest honoured number. Nothing survives a restart.
9. A door stops holding a heir when `release` is called (the harness `release` op).
10. Keys kept at removal are kept for the life of the process.
11. None. Only a number above the highest honoured is honoured, so every choice this door makes on a spent heir moves the keys.
12. The door always answers with bytes. It never gives nothing, because silence already says nothing and costs the asker no retry. A carrier gives nothing only where no door answered: an unknown ward pk, or a door that throws. Over TCP and the held line that is a 02 frame with the ask's id. On the post it is status 404 for an unknown ward pk and 204 for a door that throws. A post that is not an ask hears 405, 400 or 413.
13. `seen` is whatever the function behind the door returns: `null` for `echo`, `moved` and `null`, and `"1"` on every ask for `marked`, the empty ask included. None of them ever changes it, and none changes its describe.
14. For `echo`, `marked`, `moved` and `null`, the describe `{"asks":[]}`, the same to every asker and with no `lang`. For `silent`, silence. So no entry names any named ask, and each function answers one as the harness fixes: `echo`, `marked` and `moved` its `args`, `null` the object `null`, `silent` silence.
15. `{"object":<raw>,"seen":<seen>}`, or `{"object":<raw>,"seen":<seen>,"at":[...]}` where the function gives an `at`, with no whitespace outside the raw object, and words as `{"quo":"<word>"}`. The raw object is written as it arrived or as the function made it, and is not parsed again.
16. No padding, in what it seals or in the invitation texts it signs, because nothing it writes gains by it.
17. No. Refusals take whatever time they take. Case 1 is cheaper than case 8.
18. The refusing case and the word said go to a log function, which the harness sends to stderr.
19. The kit returns the invitation to its caller and keeps no copy. How it travels is the caller's business. The kit writes no link and reads none, and it answers no reference, because nothing here hands an invitation to a person. It writes the invitation text as `ward`, `heir`, `secret`, `lock`, then `at` where one is written, and no field beside the five, because it has nothing more to tell a holder; the ward signs that text (`Ward.invite`). Of a text it reads it takes the five, and ignores every field beside them. It shows a person none of them, because the `stand` program has no person to show them to, and Quo reads none. An invitation is refused before anything is sealed to it unless it is whole (`readInvitation`): `text` and `sig` and no third field or repeated key, a `text` denoting no lone surrogate, a text that is one object with no repeated key and the four fields of their sizes, a `sig` that is the named ward's over `quo-invitation` then the text, and a lock that passes FIPS 203's encapsulation key check (`lockOk`).
20. After a knock that brought no object: if the reply was nothing, the same knock bytes go again. If it was silence or a word, the next ask is a probe under the own key and the knock's edge key. After that, knock and probe alternate until an object comes back. A word on a probe marks the relation as bound.
21. Five seconds per address, on every carrier: a TCP frame, a held-line message and a post each read as nothing when no answer came by then, and a closed connection reads as nothing at once. An ask tried at three addresses may so wait up to fifteen seconds. Part one does not wait, because `read` hands the reply in.
22. Each ask draws a fresh key and announces it in `next`, and takes the next count number, starting at 1 for the knock. Every ask announces, because a key costs little and a standing that always announces has one path. Two sends on one relation are kept apart by a chain of promises (`Standing.chain`), so the second is sealed only after the first has been read. The standing moves only when an object comes back to an ask numbered above every ask it has moved on (`Standing.moved`). Of the keys it moved from it keeps nothing. The signing key and the edge key are dropped at the move, because no reply to an older ask can move the standing again. The knock's bytes alone are kept, for question 20's resend. When the asks after a move meet silence, a word or nothing, the standing stands where it is. It sends the next ordinary ask, numbered one higher, under the same keys. It does not knock again and it does not probe, because the move bound the relation and only a knock is ever in doubt.
23. `{ kind: "object" | "silence" | "word" | "nothing" }`, with `word` holding the word as spelled on the wire. The asker opens a reply under the edge key its ask was sent under and no other. A door's silence is sealed over the zero edge key, so on a relation it does not open, and what does not open reads as silence: one key tells the kit all it needs, and an object or a word sealed over the zero edge key reads as silence the same way.
24. Both published carriers, in all three forms, as listener and as dialer, on Node alone. Quo over TCP (`lib/tcp.js`), scheme `tcp`, with one connection per address. Quo over the web (`lib/web.js`): the post, scheme `http`, listened on with `node:http` and dialed with `fetch`, one request per ask, redirects not followed; and the held line, scheme `ws`, listened on with a WebSocket server of RFC 6455 written in the kit and dialed with Node's `WebSocket`, one line per address. The dialer also takes `https` and `wss`, because `fetch` and `WebSocket` carry TLS themselves. Their checks are Node's defaults: the certificate chain against Node's bundled roots, and the host name against the certificate. TCP is never dialed inside TLS. The listeners speak no TLS, so the kit listens on `tcp`, `http` and `ws` alone, on 127.0.0.1 at a port the system chooses. Every web listener answers on any path, and its address is written with the path `/`. The post listener sends no CORS headers, so a page of another origin cannot read its answers. A post it does not carry hears a status other than 200 and 204: 405 for a method other than `POST`, 400 for a body under sixty-five bytes, 413 for one over 1,048,640, and 404 for a ward pk it does not stand. A door that throws hears 204, as nothing. The held-line listener answers a plain request with 426, and a handshake without `quo` with 400.
25. A ward is reached by a route the caller gives (`route`, ward pk to one address), or by the invitation's `at`. The ward signed that `at` with the rest of its text, and an invitation whose signature fails is none, so every `at` the kit reads is the ward's own word. The route is the source trusted first all the same: when there is one it is dialed alone, because the caller named it. With none, the kit reads `at` (`lib/address.js`): it reads a scheme without regard to case. It skips every entry that is not a string, is not an address as its carrier writes it, or names a scheme it does not dial. It tries the rest one after another in the order written, since the first is the minting side's preference. It stops at the first reply. After an address that gave nothing, or that may have heard the box (a closed connection, or five seconds with no answer), it carries the same box to the next. A door honours a number once, so the second hearing of a box is a refusal or a choice on a number already honoured, and moves nothing. An `at` that is not an array is absent. With neither, the ask is not delivered. The kit remembers nothing of which address answered, so every ask tries `at` from its start. An `invite` that gives an `at` has it written in the invitation text as given, because the caller chose it. Where `invite` gives none and the program holds listeners, the invitation carries their addresses in `at`, `ws` first, then `http`, then `tcp`: the held line carries many asks on one connection and reaches where TCP cannot, the post reaches where a line cannot be held, and TCP is last because the web reaches further. An invitation minted with no `at` given and before any listener carries no `at`.

    The door writes `at` in a reply only where the function behind it gives one, and writes it as given. Of the harness's functions, `moved` alone gives one: `["tcp://127.0.0.1:9"]` on every object. The door knows no address itself, because its listeners belong to the program around it. The kit reads a reply's `at` as `SPEC.md` reads it. A reply carrying one is still an object, and moves the standing. Silence or a word with `at` is none of the three shapes. The kit keeps nothing of a reply's `at`, which replaces and adds nothing. The next send dials the route or the invitation's `at` as before. Keeping it would make an address the far ward chose a source this kit trusts, and nothing the kit does needs one. So its `read` carries no `at`.

26. They mean nothing to the kit. `echo` sends `args` back as it arrived. Its describe names no `lang`, so its asks mean what `SPEC.md` says of them and nothing more.
27. Inside `args`, inside `object` beyond what a describe names, and in any field beside a payload's six or beside an invitation text's five, the kit reads any JSON text the grammar allows, at any depth up to the box's size: below the second level a container is checked with an explicit stack, not recursion, and kept as raw text. Lone surrogates and noncharacters are taken as written. A repeated key inside a nested value is taken, and inside `args` too: `args` is handed on as written, its repeats with it, and `echo`, `marked` and `moved` answer it as they answer any other. So this kit refuses no text there, and beyond the box's size is only the size, which is silence. On the asking side, an `object` of any depth and any repeats is read and handed on as written, whitespace between tokens removed.
28. The kit reads no domain's vouch and shows none. The `stand` program answers the harness alone, and has no person to show a domain to. A vouch is read for a person, and here there is none.
